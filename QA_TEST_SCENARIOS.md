# Whistleblowing Portal — QA Test Scenarios and Test Cases

## Scope and test basis

Application tested: `https://aura-web-whistleblowing-test.apps.cih-main.qo4k.p1.openshiftapps.com/`

The cases below are derived from the pages and controls visible in the application. No requirements or design specifications were provided.

Status meanings:

- **Passed**: the observed behavior matched the objective.
- **Failed**: the observed behavior contradicted the objective or exposed an apparent product defect.
- **Not tested**: behavior could not be verified without a valid test dependency, a destructive submission, a file, or an unavailable service.

Assumptions are stated where the application does not expose a verifiable requirement. Payment and registration were not visible anywhere in the observed flows; therefore, no payment or registration test cases are invented.

## Mandatory precondition and step format

For execution, the first line of the **Steps** field for every case is the precondition. Use the following wording before the numbered actions shown in each case:

`Precondition: The QA environment is reachable; the tester has opened the route stated in the first step; the browser is supported; the input data listed in the case is available; and no unexpected session, modal, or previous test data is present unless the case explicitly requires it.`

Apply these case-specific additions to that precondition where relevant:

- Report wizard cases: the tester is unauthenticated, a new browser session is used, and no report is submitted unless the case explicitly says to submit one.
- Follow-up cases: a valid reference/access-code pair is available only for positive cases; fabricated or mismatched values are used for negative cases.
- Login cases: a valid QA account is available only for positive authentication cases; invalid credentials are used for negative cases.
- Upload cases: a safe test file of the stated type and size is available, and the file picker is permitted.
- Integration cases: the required service, database, session, role, and network condition are prepared before step 1.
- Unit cases: the component or validation function is isolated, reset before execution, and supplied with the input data stated in the case.

The numbered actions must then be executed in order. After each action, record the observed result before proceeding. If a precondition cannot be satisfied, mark the case **Not tested** and document the missing dependency in the result.

## Findings and assumptions

1. The product is anonymous-report capable and explicitly states that registration is not required.
2. No payment page, payment control, registration page, or payment-related field appeared in the tested navigation; payment is therefore out of the observable scope.
3. A real report was not submitted because submission creates an external case and requires preserving generated credentials. Submission and valid follow-up remain untested.
4. The public pages emitted pre-login service warnings for missing session-token-backed system text/lookups, and invalid login displayed “Login service unavailable”. Successful authentication and role-based permissions require a functioning authentication service.
5. The displayed external support links appear to be placeholders or test fixtures. This is recorded as an observation, not as a requirement inferred from the site.
